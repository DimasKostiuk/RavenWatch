# RavenWatch: архітектура всього моду

Прочитай це перед будь-якою зміною коду моду.

**Головне правило: спершу знайди місце в ядрі.** Майже кожна велика частина моду вже має одне місце, через яке проходить уся її робота. Якщо поведінка неправильна, виправляй її там, де вона народжується. Не додавай поруч другий механізм, таймер, менеджер чи «рятівника». Те, що нова система замінює, видаляй, а не лишай поруч.

Якщо ядро справді не вміє потрібного: розшир ядро або скажи користувачу, чого бракує, і запропонуй варіанти. Обхід мовчки не роби.

**Друге головне правило: без зайвих важких викликів.** Там, де важкий виклик справді потрібен, він дозволений, але має бути прогнозованим і якомога легшим: заздалегідь відомо, коли він спрацює, як часто і скільки роботи зробить.

Шапка кожного файлу пояснює його роботу, тож прочитай її, перш ніж чіпати файл. Нижче вказано, куди дивитися насамперед.

## Хто за що відповідає

### Ворон: тіло й рух

| Що потрібно | Єдине місце | Не роби |
|---|---|---|
| Будь-який політ ворона | `RavenFlight` (`FlightBody`), `RavenMotor` (`Motor.cs`), плани в `FlightPlans` | власний шлях польоту |
| Хто зараз керує вороном | `AnimDirector.Take` / `Release`: сильніша дія забирає птаха у слабшої | рухати птаха, не взявши його |
| Анімація ворона | наші кліпи й ключі крил | кліпи ворони, чайки, валькірії |
| Ворон на плечі | `Shoulder` (малювання за даними гравця), `RavenSeat` (місце), `ShoulderLife` (життя) | слот гри для ворона |
| Сидіння ворона на жердині | `Perches`, `PerchView`, `PerchLife` | окремі місця для кожної будови |
| Сюжетний ворон і ворон NPC | `StoryBird` (картинка без мережевого об'єкта), `NpcRaven` | ще один тип птаха |

### Сумісність і мережа

| Що потрібно | Єдине місце | Не роби |
|---|---|---|
| Дані на гравці | `NetFlag.Zdo` | свої способи |
| Патч на код істот, бою, ШІ, спорядження гри | обгортка `try` + `PatchGuard.Fail` | патч без захисту: він ламає метод гри |
| Інші моди | мод працює на чистій грі, залежності м'які. Читай чужий код лише щоб зрозуміти | копіювати чужий код |
| Шукати об'єкт гри | брати оригінал гри, а не копію іншого мода | |

### NPC

| Що потрібно | Єдине місце | Не роби |
|---|---|---|
| NPC іде кудись | `NpcMind.Move` → `NpcWalk.Step` → `NpcMind.Steer` | ігровий `MoveTo` / `MoveTowards`: на повороті понад 10° NPC зупиняється |
| Шлях тримається далі від країв | `NpcWalkRoom` | правки шляху у викликах |
| NPC застряг | драбина в `NpcWalkStuck`, нового кроку додай туди | новий таймер «застряг» |
| Ціль недосяжна | `NpcWalk.CantReach`, `KeepOff`, `Avoided` | повторні спроби у викликах |
| Перенести тіло | лише як запобіжник, через `NpcWalk.Jumped`; на очах у гравця лише з димком (`NpcActor.Appear`) | телепорт для зручності |
| Сісти, встати, лягти | `NpcBody.Attach` / `Detach` | ставити тіло напряму |
| Кістки NPC | новий шар у `NpcPose`: анімація гри → кліпи → хода → падіння → їжа | власний `LateUpdate`, що правив би кістки |
| Читати кістку NPC чи гравця | `BodyClips.SkeletonBone`; для NPC у пізнішому порядку виконання, ніж `NpcPose` | `Utils.FindChild`: знаходить кістки одягу й воронів на тілі |
| Рука чи нога до точки, голова на ціль, плавна крива | канали кліпу `@LeftHand`, `@RightHand`, `@LeftFoot`, `@RightFoot`, `@Look` і рядок `curve ease` у `BodyClips` (шапка файлу) | свій розв'язувач кісток у модулі |
| Анімація тіла | кліп у `BodyClips`, програє `BodyAnimator`; на NPC `NpcBody.Clip`: кліп без строку, який сам не закінчується (`loop`, `hold`, `drive`), отримує `LoopTerm` (60 с), довший сцена пише секундами | другий програвач; свій таймер, щоб зняти кліп. Перед роботою над кліпом прочитай `docs/ANIMATION.md` |
| Сцена тримає NPC | блокування `KScene` у `StoryScenes`; коли його ніхто не поновлює, господар NPC сам відпускає все, що тримала сцена (`NpcMind.SceneWatch`, `LetGo`) | окремий рятівник для сцени, що обірвалась |
| Вхід і вихід кліпу | сам кліп: рядок `fade` (без нього 0.7 с), ядро не дасть менше | короткий fade при виклику, щоб «пришвидшити» |
| Ноги на нерівній землі | рядок `feet ground` у кліпі | піднімати ноги в самому кліпі під конкретний схил |
| Момент усередині кліпу | рядок `mark` у кліпі, крок сцени `player mark` | рахувати секунди в сцені |
| Кліпи для гри | `assets/story/clips`; файл у конфігу важить більше, це для живої правки | нові кліпи рядками в коді |
| Шматок кліпу (сів / дивиться в циклі / встає) | рядок `part` у кліпі дає окремий кліп `<кліп>.<частина>` | окремі файли-шматки, власне перемикання |
| Жести гравця | `Gestures` (режисер), поза сцени через `Gestures.Scene` / `SceneEnd` | грати кліп повз нього |
| Взяти зі скрині чи покласти | відкрити: `NpcMind.Open(скриня, секунди)` (зайнята чи чужа — ні; власник, віко, обличчям, рух); з паузою руки: `NpcMind.Reach(скриня, ref мить)`: обличчям, віко (`NpcLid`), рух руки гри; так їжа з комори й платня зі скарбнички | своє відкривання скрині в модулі |
| Двері | `NpcDoors`. Команда гри є перемикачем | свій виклик `UseDoor` |
| Частина NPC | реєстрація в `NpcModules`, власний файл | ядро, що знає модуль на ім'я |
| Завдання NPC | шари `NpcMind`: Leisure < Routine < Job < Whim < Order < Fight < Scene. У кожного плану є власник (`Plan.Whose`): `Do`/`Order(слова, шар, чий)`, `Put(шар, план, чий)`. `free` і `Put(null)` знімають лише свій план і те, що власник поставив на шарі (погляд, манеру бою: вони окремі для кожного шару й того, хто їх поставив; діє найвищий шар). Чужий план перебиває лише правило ядра `NpcMind.May`: на сцені stage > story > rescue, на примхах обов'язок > розвага, на інших шарах останнє слово | обходити пріоритети; знімати чужий план; ставити погляд чи бій "назавжди" поза своїм шаром |
| Примха NPC (будь-яка підсистема «оживлення») | `NpcMind.TakeWhim(план, секунди, чия)` і `EndWhim(чия)`: завжди зі строком і власником; розвага (`NpcMind.Leisure`, `NpcWhims`) поступається обов'язку (платня, їжа, відпочинок від утоми), обов'язок не перебиває інший обов'язок; перевірка "чи можна": `WhimFree(чия)` | `Put(Layer.Whim, …)`: ядро його відхиляє |
| Наказ NPC з будь-якої гри | `NpcActor.Order`: сам відправить господарю. Прямі `Mind.Do`/`Put`/`TakeWhim` на грі, що не веде NPC, ядро відхиляє з записом у лог | писати в розум NPC повз `Order` |
| Хто веде NPC змінився | `NpcActor.OwnerChanged` → `NpcMind`, `NpcBody`: пам'ять старого господаря не вважається правдою, правда в ZDO | свій `_wasOwned` у модулі для стану, що важить після передачі |
| Частина модуля зламалась | `NpcActor.Run` (`Ticks`, `Everywhere`, `Removed`, `Unloaded`, `BeforeDressed`): пише в лог, пауза 30 с лише цій частині; збій думки: `NpcMind.ThinkFailed` відпускає план, пауза 2 с | свій `try` навколо цілого кадру |
| NPC іде за гравцем | `follow`: `Plan.Leader` тримає номер гравця, тому смерть гравця й перезапуск плану не рвуть; гравця нема 30 с — план відпускається на будь-якому шарі. Слово квесту `npc <хто> follow` живе в ZDO (`StoryActions.LeadWatch`) | зберігати ZDOID гравця як правду |

## Правила для всього моду

- **Плавно за замовчуванням.** Ворон, NPC, вогонь, ефекти з'являються і зникають поступово. Політ і хода без різких зупинок і телепортів, обмеження лише плавні.
- **Мережа.** Хто керує об'єктом, той вирішує й пише в ZDO лише за зміни. Інші малюють за цими даними. Те, що має пережити зміну власника чи перезапуск, зберігай у ZDO чи предметі, а не в полі класу.
- **Важкі виклики** (пошук по сцені, обхід усіх істот, фізика на область, `GetComponentsInChildren`, створення об'єктів, файли; перевірка рахує лише перші чотири, решту стеж сам):
  1. Спершу візьми готове: `Senses`, `NpcCensus`, `NpcFoes`, збережений результат.
  2. Запускай за подією, а не щокадру. Якщо треба опитувати, то рідким таймером.
  3. Не роби все в один кадр: розподіляй роботу між кадрами й обмежуй її кількість за кадр.
  4. Невдалу спробу не повторюй одразу: зроби паузу.
  5. Де виклик потрібен, напиши в його рядку, коли і як часто він спрацьовує: `// heavy: раз при завантаженні`.
  6. Заміряй «до» і «після»: `Perf` для воронів, `NpcPerf` для людей.
- **Постійні зв'язки.** ZDOID змінюється при кожному завантаженні світу, тому збережений `user:id` після перезапуску нікуди не веде. Зберігай через `NpcKit.Save` / `Resolve`. Якщо значення живе лише одну сесію, напиши `// session: чому`.
- **Помилки не ховай.** `catch` записує причину в лог. Якщо мовчання тут правильне, напиши `// quiet: чому`. Обгортка навколо незнайденої причини не є виправленням. Перевірку на `null` роби один раз на вході, а не в кожному шарі.
- **Нове для гравця (механіка, нагорода, модифікатор):** спершу покажи варіанти й перевір, чи цього ще немає в коді.
- **Коли щось не працює:** знайди справжню причину й поясни її. Не змінюй наосліп кілька разів поспіль.
- **Прибирай за собою:** зайвий код, тестові файли, знімки студії.
- **Документи для гравців:** CHANGELOG короткий, без чисел і нутрощів; у README немає команд консолі.
- **Шляхи й збирання:** `tools/rw_build.ps1`; збирати лише поточну версію; перед збиранням подивись `releases/`.

## Перед словом «готово»

Кожне питання взяте з помилки, яка вже траплялася:

1. **Що буде, коли дія не вдасться?** Чи не повторюватиметься вона щокадру чи щосекунди?
2. **Що буде при зміні власника об'єкта або перезапуску?** Чи не лишиться старий стан у ZDO, чи не загубиться потрібний?
3. **Чи показує вимірювач правду?** Перш ніж вірити теорії, перевір сам інструмент.
4. **Це причина чи симптом?** Якщо причини не знайдено, так і скажи.
5. **Чи не вимірюється один раз те, що рухається?** Могила, щогла, голова, сидіння.
6. **Скільки це коштує?** Як часто спрацює і скільки об'єктів обійде, коли в грі 10 NPC і 5 гравців.
7. **Чи бачили це в грі?** Якщо ні, додай у `docs/UNTESTED.md` і не кажи, що воно працює.

## Перевірка

- **`rw_build` сам запускає** `tools/arch_check.js` (ці правила), `tools/storycheck.js` (стадії, сцени, місця й люди в `assets/story` існують), `tools/clipcheck.js` (кліпи й ті, що названі в сценах) і перевірки фраз (`talkcheck`, `bookcheck`). Перевірка зупиняє збірку. Не обходь її. Дозвіл-виняток у ній додавай лише з явної згоди користувача.
- **Старий код не зупиняє збірку, але й рости не може.** `tools/arch_baseline.json` тримає для кожного файлу кількість: `catch`, що нічого не пише; збережених `user:id`; важких викликів; патчів без `PatchGuard`. Виправив старе: запусти `node tools/arch_check.js --tighten`, числа лише зменшуються. Нове проходить через ядро або з поясненням у своєму рядку: `// quiet:`, `// session:`, `// heavy:`. Пояснення має бути правдивим, це не виняток. Для патчів пояснення немає: лише `PatchGuard`. Піднімати числа, запускати `--new-baseline` і додавати винятки можна лише зі згоди користувача.
- **Що перевірка не бачить:** задум (другий менеджер своїми словами), частоту виклику, правдивість пояснення, ключі налаштувань у змінних, слова кроків сцен і умов (їх перевіряє сама гра при завантаженні, у лог).
- **Неперевірене в грі:** `docs/UNTESTED.md`. Не будуй поверх цього так, ніби воно працює.
- **Окремо за потреби:** `tools/lint.js`, `phrasecheck.js`, `chaincheck.js` для фраз.
